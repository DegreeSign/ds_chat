@degreesign/chat vs @mlc-ai/web-llm

Both packages run google/gemma-4-E2B-it on WebGPU inside the browser. The difference is what each one asks of the tab: the download, the context window, the adapter, and the code the host has to write.

01 A headless client, not a chat demo

chat owns the model lifecycle and one streaming generation. It renders no markup, ships no styles, and keeps no copy. The host passes messages and callbacks and owns the entire interface. The same package runs in React and in Node, imports no DOM at load time, and reports an unsupported status instead of throwing when there is no browser.

web-llm is an inference engine with an OpenAI-shaped chat API. The host still builds the progress surface, the device strategy and the fallback story.

The GPU engine and the CPU engine both ship inside the package and load as separate chunks. A host installs one dependency and resolves no engine, no wasm path and no model URL.

Engine selection is automatic. The client probes for a WebGPU adapter with a 1500 ms timeout. An adapter selects the Gemma 4 build, and no adapter selects a Qwen3-VL 2B model on the CPU. The host reads which engine ran and which build loaded, so the interface can label itself honestly.

03 The shader-f16 gate decides who runs at all

web-llm marks its Gemma 4 f16 build with a required shader-f16 feature. Headless Chromium 156 on this machine exposes an AMD gcn-4 adapter (Radeon RX Vega M GH) and reports no shader-f16. Its SwiftShader fallback reports none either.

On that hardware only the web-llm f32 build starts. The LiteRT engine needs only a WebGPU adapter, so the 2.0 GB Gemma 4 build runs there. GPUs without f16 support are not a corner case in consumer hardware, and a client that fails to initialize on them loses those users entirely.

The Gemma 4 build is text only and carries no vision or audio encoder, which is what keeps the download at 2.0 GB. Images go through Qwen3-VL on the CPU, where the projector adds 445 MB.

Both Gemma 4 builds for web-llm are 2.8 GB, and the f16 build also declares 3387 MB of VRAM, the f32 build 3863 MB. The same base model costs 800 MB more before a single token is generated.

Downloads resume. Weights land in 32 MB parts, an interrupted transfer keeps every committed part, and the next attempt continues from the last one, including after a page reload. The client asks the browser for persistent storage before a load so the weights survive eviction pressure.

05 Context and prefill headroom

Windows the engine is asked for

GPU context, desktop 32768 4096
GPU context, mobile 16384 4096
Prefill chunk engine managed 512
CPU context8192 desktop, 4096 mobile no CPU path

A 4096 token window is a short conversation. It fits a question and a brief answer, then the oldest turns fall out. The GPU path in this package carries four times that on a phone and eight times that on a desktop, which is the difference between a single prompt and a working chat history.

The 512 token prefill chunk in web-llm also caps how much of a long prompt the GPU ingests per step. Long system prompts and multi-turn history are exactly what consumer chat products send.

The package is the larger install, and that is the honest number. It is 50.2 MB unpacked because both engine builds ship inside it: the host installs one dependency and resolves no wasm path. A page still fetches only the one path it runs, so no browser pays for both engines.

07 Media without a second stack

Image description and translation are part of the package, not an add-on. A batch of images is described in English on the CPU vision model, then translated one image at a time on the GPU Gemma 4 build. Without an adapter, or when the translator declines, the English text is kept.

Every result carries the English description, the translated description and the duration of that image. A host can stop a batch and keep every finished image, append its own rules to the describer prompt, and set the vision token budget per image.

The GPU build is text only, so image turns run on the CPU model while translation runs on the GPU. web-llm's Gemma 4 build declares audio but has no vision path, so an image feature needs another stack.

08 Tools and grounding included

The package ships web search, arithmetic and currency tools, with Wikipedia and DuckDuckGo as search providers. A host defines a tool as a schema plus a function, and receives parsed calls and results. The tool layer is part of the same install, so grounding a local model in live data needs no extra dependency or glue code.

09 Behaviour under real UI conditions

  • The newest request owns the model, and a superseded request delivers nothing.
  • Cancelling aborts the generation and unloads the model, so the next turn starts from a fresh context instead of inheriting a broken one.
  • A failed generation unloads the model for the same reason.
  • A cancel during a shared load lets that load finish and reports its own outcome.
  • Streamed text arrives accumulated, ready to assign to a view, with a token speed callback and a status snapshot covering phase, percent, engine and capability flags.
  • Download and load share one progress channel, so the interface needs one bar, not two.

10 Small models are not a chat substitute

web-llm's catalog reaches much lower than this package. It can start a 135M parameter model in a tab, and it lists several builds under 1 GB of declared VRAM:

Those builds fit a small tab and start fast, and they are the reason web-llm looks attractive on paper. Every one of them is too weak for a chat product. The 135M and 360M models answer in fragments. The 0.5B to 2B builds open with a sentence that looks right, then forget the instruction, invent facts, repeat themselves, and fail simple arithmetic. None of them is usable as an assistant. They are classifiers, extractors, autocomplete engines or demo filler, and they only look adequate until a real user types a second question.

Gemma 4 E2B at 2.0 GB is the smallest build in either package that carries a conversation: it follows the system prompt, keeps names and numbers across turns, and reasons through a short task. That is the floor for chat, and it is the model this package ships.

Choose @degreesign/chat for consumer web apps, mobile PWAs and cross-platform clients where download size, memory, hardware coverage, context length and a predictable UI contract decide whether the feature ships.

Choose @mlc-ai/web-llm for desktop-only tools pinned to high-end adapters that expose shader-f16, where a broad model catalog matters more than the client budget.
